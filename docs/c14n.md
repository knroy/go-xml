# Canonical XML (`c14n`)

Package [`c14n`](../c14n/) implements the three canonicalization algorithms
that XML security standards name:

| Algorithm | Specification | Constants |
|---|---|---|
| Canonical XML 1.0 | [W3C REC 2001-03-15](https://www.w3.org/TR/2001/REC-xml-c14n-20010315) | `Inclusive10`, `Inclusive10WithComments` |
| Exclusive Canonical XML 1.0 | [W3C REC 2002-07-18](https://www.w3.org/TR/2002/REC-xml-exc-c14n-20020718/) | `Exclusive10`, `Exclusive10WithComments` |
| Canonical XML 1.1 | [W3C REC 2008-05-02](https://www.w3.org/TR/2008/REC-xml-c14n11-20080502/) | `Inclusive11`, `Inclusive11WithComments` |

Canonicalization turns a document, or a subset of one, into a byte-exact
serialization: two inputs that differ only in insignificant ways — attribute
order, quote style, `<e/>` against `<e></e>`, redundant namespace declarations,
character references — produce identical octets. Everything a signature
covers is covered in this form, which is why the algorithm is the foundation of
every XML signature scheme.

It is for you if you are implementing or verifying:

* **XML-DSig** — `ds:CanonicalizationMethod` and the `Transform` chain of a
  `ds:Reference`.
* **SAML** assertions and responses, which are signed with XML-DSig and
  canonicalized with Exclusive C14N almost without exception.
* **WS-Security** SOAP message signatures.
* **XAdES** — e-invoicing (Peppol, UBL, the EU's eIDAS signatures) sits on it.
* **ODF and OOXML** document signatures.

And, outside security:

* **Content addressing** — a hash of the canonical form is a stable key for a
  cache or a content-addressed store, however the document happened to be
  serialized.
* **Semantic equality** — `Equal` answers "are these the same document?"
  without a hand-written tree comparison.

The package depends on [`xdm`](../xdm/) and [`xpath`](../xpath/) only. It adds
no module dependency and no cgo, so it cross-compiles like the rest of go-xml.

---

## Quick start

```go
tree, err := xdm.ParseString(src, xdm.ParseOptions{})

// The canonical octets.
b, err := c14n.Bytes(tree.Root, c14n.Options{Algorithm: c14n.Inclusive11})

// A digest, streamed: the canonical form is never materialized.
sum, err := c14n.Digest(sha256.New(), elem, c14n.Options{Algorithm: c14n.Exclusive10})

// Semantic equality.
same, err := c14n.Equal(a.Root, b.Root, c14n.Options{Algorithm: c14n.Inclusive11})
```

`Bytes`, `Digest` and `Write` take a document node (the whole document) or an
element node (that element and its descendants, treated as the apex of a
subset). Each has a `…NodeSet` twin — `BytesNodeSet`, `DigestNodeSet`,
`WriteNodeSet` — that takes an arbitrary [node set](#node-sets).

`Equal` stops at the first differing octet: it buffers one canonical form and
streams the other against it.

## Choosing an algorithm

**There is no default, and the zero `Options` is an error** (`ErrNoAlgorithm`).
Every specification that uses canonicalization names the algorithm, and the
most damaging mistake in this domain is canonicalizing silently with the wrong
one: the signature it produces is accepted by no peer, and no local test
detects it, because the local verifier made the same choice. So the choice is
always yours to spell out.

`Algorithm` is the W3C URI, deliberately: the value you read out of a
`ds:CanonicalizationMethod/@Algorithm` or a `ds:Transform/@Algorithm` can be
passed through unchanged, and `Algorithm(s).Valid()` checks it. Anything else
is `ErrUnsupportedAlgorithm`, wrapped with the offending value.

Choose by the specification you are implementing, never by preference. As a
guide to what those specifications say:

* **Exclusive C14N** when a signed fragment may be moved into a different
  document — a SAML assertion inside a response, a SOAP body inside an
  envelope. It renders only the namespace declarations an element *visibly
  uses* and never copies `xml:*` attributes down from outside the subset, so
  the fragment canonicalizes the same wherever it lands. SAML, WS-Security and
  most signed-message profiles require it.
* **Inclusive C14N 1.0** when the signature is over a whole document that
  stays where it is, and the specification names 1.0 — the XML-DSig default,
  and what older profiles use.
* **Inclusive C14N 1.1** when the specification names it. It is 1.0 with two
  corrections for subsets, described [below](#what-c14n-11-changes).

The `WithComments` variants keep comments; the others drop them. A
same-document reference (`URI="#id"`) is canonicalized *without* comments even
when the transform names a `WithComments` algorithm — XML-DSig's reference
processing model says so — and applying that rule is the caller's decision,
not this package's.

## Node sets

The specifications define their input as an XPath 1.0 node set. A `NodeSet`
here is an interface — `Root()` and `Contains(n)` — and six constructors cover
the cases the consuming specifications produce:

| Constructor | The set | Typical source |
|---|---|---|
| `Subtree(n)` | `n`, its descendants and their attributes | a same-document reference `URI="#id"` |
| `Document(d)` | the whole document containing `d`, document node included | `URI=""` |
| `ExcludeSubtree(root, x)` | `root`'s subtree minus `x` and everything under it | the enveloped-signature transform |
| `Func(root, f)` | the nodes of `root`'s subtree for which `f` is true | anything else you can compute |
| `FromXPath(doc, expr, ns)` | the nodes `expr` selects; namespace declarations follow their elements | a node-set expression you write |
| `FromXPathFilter(doc, filter, ns)` | every node, namespace nodes included, for which `filter` is true | the XML-DSig XPath Filter transform (`http://www.w3.org/TR/1999/REC-xpath-19991116`) |

Both compile the expression as XPath 2.0, which accepts almost every XPath 1.0
transform expression unchanged. `FromXPath` evaluates once and tests
membership against the result. `FromXPathFilter` evaluates the filter as a
boolean with every node as the context node, as XML-DSig defines the
transform, so it is the one to use for a `ds:Transform`; the `here()` function
is not provided. `ExcludeSubtree` is faster than either and should be
preferred where it applies. `Func`'s predicate is called at most once per
node, in document order, and must be deterministic.

### Example: an exclusive subtree with an InclusiveNamespaces prefix list

A SOAP body whose content uses a namespace prefix inside an attribute *value*
— `xsi:type="t:OrderType"` — is the textbook case. Exclusive C14N sees only
prefixes used in element and attribute *names*; the `t` in the value is
invisible to it. Without help, the declaration of `t` is dropped, the
canonical form no longer says what `t:OrderType` means, and a verifier that
re-parses it cannot resolve the QName. The `ec:InclusiveNamespaces` element's
`PrefixList` exists to name such prefixes:

```go
src := `<soap:Envelope xmlns:soap="http://www.w3.org/2003/05/soap-envelope"
               xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
               xmlns:t="urn:example:types" xmlns:unused="urn:unused">
  <soap:Body Id="body">
    <Order xsi:type="t:OrderType"><Item sku='A-1'   qty="2"/></Order>
  </soap:Body>
</soap:Envelope>`

tree, err := xdm.ParseString(src, xdm.ParseOptions{})
body := tree.Root.Children[0].ChildElements()[0]

// PrefixList="t", as read from <ec:InclusiveNamespaces PrefixList="t"/>.
out, err := c14n.Bytes(body, c14n.Options{
    Algorithm:                  c14n.Exclusive10,
    InclusiveNamespacePrefixes: c14n.ParsePrefixList("t"),
})
```

produces

```xml
<soap:Body xmlns:soap="http://www.w3.org/2003/05/soap-envelope" xmlns:t="urn:example:types" Id="body">
    <Order xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xsi:type="t:OrderType"><Item qty="2" sku="A-1"></Item></Order>
  </soap:Body>
```

Note what each declaration did. `soap` is rendered on `soap:Body` because the
element uses it; `xsi` is rendered on `Order`, not on the apex, because that is
the first element that uses it; `t` is rendered on the apex because the prefix
list forces it; `unused` appears nowhere. Without the prefix list the
`xmlns:t` is simply absent. Inclusive C14N would render all four on
`soap:Body`.

`ParsePrefixList` maps `#default` to the empty string (the default namespace)
and drops repeats; `FormatPrefixList` is its inverse. A prefix that is not in
scope renders nothing and is not an error. The inclusive algorithms ignore the
list, so a caller forwarding a parsed transform's parameters need not branch.

### Example: the enveloped-signature transform, digested with SHA-256

An enveloped signature sits inside the document it signs, so the reference
digests the document *minus the `ds:Signature` element* — the
`http://www.w3.org/2000/09/xmldsig#enveloped-signature` transform. That is
`ExcludeSubtree`:

```go
src := `<Invoice xmlns="urn:inv" xmlns:ds="http://www.w3.org/2000/09/xmldsig#">` +
    `<Total currency="EUR">100.00</Total>` +
    `<ds:Signature><ds:SignedInfo/><ds:SignatureValue>abc</ds:SignatureValue></ds:Signature>` +
    `</Invoice>`

tree, err := xdm.ParseString(src, xdm.ParseOptions{})
var sig *xdm.Node
for _, e := range tree.Root.Children[0].ChildElements() {
    if e.IsElement("http://www.w3.org/2000/09/xmldsig#", "Signature") {
        sig = e
    }
}

set := c14n.ExcludeSubtree(tree.Root, sig)
sum, err := c14n.DigestNodeSet(sha256.New(), set, c14n.Options{Algorithm: c14n.Inclusive10})
fmt.Println(base64.StdEncoding.EncodeToString(sum))
// 1MEm4cLHKqUziQkiiqmfVhP1Eb9W2rZd2XaxSOi5CSY=
```

The octets digested are

```xml
<Invoice xmlns="urn:inv" xmlns:ds="http://www.w3.org/2000/09/xmldsig#"><Total currency="EUR">100.00</Total></Invoice>
```

The `xmlns:ds` declaration stays, because it is on `Invoice`, which is in the
set. The equivalent XPath Filter, `FromXPath(doc, "//node()[not(ancestor-or-self::ds:Signature)] | //@*[not(ancestor::ds:Signature)]", ...)`, gives
the same octets; it is shown only to make the correspondence plain.

Finding the right `ds:Signature` — the one that contains the reference being
verified, not merely the first in the document — is the caller's job, and the
subject of a whole class of signature-wrapping attacks. This package
canonicalizes the set it is given; it does not choose it.

### Namespace nodes

The XPath 1.0 data model the specifications were written against has
*namespace nodes*, one per in-scope binding per element, and a node set may
contain some of an element's namespace nodes and not others.

**By default an element's namespace declarations participate exactly when the
element does.** That is what every consuming specification's usual node sets
produce: a same-document reference is a subtree, and the enveloped-signature
transform's `//namespace::*` keeps every namespace node of every kept element.
`Subtree`, `Document`, `ExcludeSubtree`, `Func` and `FromXPath` work this way.

**A node set that decides namespace-node membership itself implements
`NamespaceSet`**, which adds `ContainsNamespace(elem, prefix)`. Canonicalization
then follows the namespace-node rules literally:

* an element may keep some of its namespace nodes and not others;
* an element **outside** the set still renders its namespace nodes that are
  inside it, as text in the parent's content (C14N 1.0 §2.3). The result is
  not well-formed, and it is what the specification says;
* under Exclusive C14N, a PrefixList prefix follows those Canonical XML rules,
  while any other visibly utilised prefix renders when its element is in the
  set, whether or not its namespace node is (§3).

`FromXPathFilter` returns a `NamespaceSet`, because the XPath Filter transform
filters namespace nodes like any other. An undeclaration (`xmlns=""`) creates
no namespace node, as in XPath 1.0 §5.4, so there is nothing of it to keep or
drop.

### Refused input

Two inputs the specifications do not define are refused rather than given an
output nobody can reproduce:

* **XML 1.1 documents.** C14N 1.1 "is applicable to XML 1.0 … It is not defined
  for XML 1.1", and 1.0 and Exclusive C14N share its data model. The parser
  reads XML 1.1, and records the declared version on `xdm.Tree.XMLVersion`;
  `c14n` refuses a tree that says `1.1` with `ErrXML11`. Canonicalizing one
  anyway would write a character XML 1.1 allows only as a reference (`&#1;`)
  raw, which is well-formed in neither version. A tree an XSLT transform built
  declares no version and is read as 1.0.
* **Relative namespace URIs.** C14N 1.0 and 1.1 §2.1: implementations "MUST
  report an operation failure on documents containing relative namespace
  URIs". Every declaration the walk visits, and every binding in scope above
  its start, must be absolute (have a scheme, RFC 3986 §4.3), or the result is
  `ErrRelativeNamespaceURI`. `xmlns=""` is an undeclaration, not a URI. The
  parser still accepts relative namespace URIs, which Namespaces in XML
  deprecates rather than forbids; only canonicalization refuses them.

## What C14N 1.1 changes

C14N 1.1 is 1.0 with two corrections, both about `xml:*` attributes on
ancestors that are *outside* the subset:

* **`xml:id` is not inherited.** 1.0 copies every `xml:*` attribute from
  omitted ancestors onto the subset's apex. Copying an ID produces a second
  element with the same ID, so 1.1 copies only `xml:lang` and `xml:space`.
* **`xml:base` is fixed up, not copied.** 1.0 copies the nearest ancestor's
  `xml:base` verbatim, which is wrong whenever the apex's own `xml:base` is
  relative to it. 1.1 joins the omitted ancestors' values with the apex's own
  by the specification's join-URI-References (§2.4, a variant of RFC 3986
  §5.2 that lets two relative references combine into a relative one).

```xml
<doc xml:base="http://example.org/a/" xml:id="d1" xml:lang="en">
  <sec xml:base="b/"><p xml:base="c.xml">x</p></sec></doc>
```

Canonicalizing `p` alone:

| Algorithm | Output |
|---|---|
| `Inclusive10` | `<p xml:base="c.xml" xml:id="d1" xml:lang="en">x</p>` |
| `Inclusive11` | `<p xml:base="http://example.org/a/b/c.xml" xml:lang="en">x</p>` |
| `Exclusive10` | `<p xml:base="c.xml">x</p>` |

**The fix-up is URI arithmetic and nothing else.** No base is resolved against
a document location and nothing is fetched; the inputs are the attribute
strings and the output is a string.

Exclusive C14N inherits no `xml:*` attribute at all, by design: propagating
`xml:lang` or `xml:base` into a subtree is exactly what would stop it being
relocatable. That omission is the algorithm, not a gap.

### One deliberate divergence from the literal text

When a node set keeps an element but drops that element's **own** `xml:lang`,
`xml:space` or `xml:base` attribute, and the element is the apex of the subset
(its parent is omitted), `Inclusive11` still renders the attribute. §2.4 read
literally merges only "the nodes of E's attribute axis that are in the
node-set". The XML Security Working
Group's interop case `xmlbase-c14n11spec3-103` expects the opposite: its filter
`self::a or ancestor-or-self::d` keeps `a` without its `xml:base`, and the
expected output is `<a xml:base="foo/bar">…`, which all five implementations in
that round (IAIK, IBM, Oracle, Sun, UPC) signed. The Working Group's result is
followed, because it is the W3C's own evidence of what the text means and
because it is what the Java XML-DSig stack most Peppol access points run on
produces. `xml:id` is not affected, nor are `Inclusive10` and `Exclusive10`, and
no whole-document, `#id`, or `ExcludeSubtree` input can reach the case.
`xmlsec1` 1.2.41 (libxml2 2.9.14) was measured producing the Working Group's
result on this case too, in the `xmlsec1` differential below.

## Security

* **Depth is bounded.** `c14n.MaxDepth` (default **500**) bounds element
  nesting below the node a canonicalization starts from; deeper input fails
  with `ErrDepthExceeded` rather than exhausting the stack. It is a package
  variable so a caller with unusual input can raise it knowingly; it is read
  once at the start of each canonicalization, and changing it concurrently
  with one is a data race. Zero or negative means the default, as it does
  for `xdm.ParseOptions.MaxDepth`; there is no unlimited setting, because the
  walk recurses. The parser's own `MaxDepth` applies first.
* **A DOCTYPE is refused by the parser**, unless the caller parsed with
  `AllowDOCTYPE`. The input is an `xdm` tree, so every parser default —
  DOCTYPE refusal, the entity-expansion budget, the size and node limits —
  applies unchanged. C14N requires entity references and DTD default
  attributes to be expanded in the canonical form; the parser does that when
  a DOCTYPE is permitted, and this package never sees an unexpanded one.
* **Nothing is fetched.** No network access, no filesystem access, from any
  entry point, including the 1.1 `xml:base` fix-up.
* **Inclusive C14N over a subset can amplify its input, by specification.**
  Every apex of an inclusive canonicalization — every element whose parent is
  outside the set — carries every namespace binding in scope. A document
  that declares many prefixes near its root and a node set with many apexes
  (one per leaf, say) therefore produces output of order *apexes × bindings*:
  a 127 KB document with 1,000 declarations and 10,000 leaf apexes
  canonicalizes to 198 MB. Time is linear in that output (about 8 ns per
  byte), and `Digest` streams it, so memory stays flat — but the CPU is
  spent. This is the algorithm, not the implementation; Exclusive C14N does
  not amplify (68 KB for the same input). In XML-DSig the node set comes from
  the signature's own `Transforms`, which an attacker writes, so a verifier
  accepting untrusted signatures should restrict XPath Filter transforms over
  inclusive canonicalization — the reason hardened verifiers such as Apache
  Santuario's secure-validation mode do. Whole documents, `#id` references
  and `ExcludeSubtree` have one apex and cannot amplify.

  **There is deliberately no output cap here.** Which transforms a signature
  may use, and over what, is signature policy, and it belongs in the
  signature layer that parses the `Transforms` — `go-xmlsec` — where it can
  refuse the transform before any canonicalization runs, rather than in a
  byte limit that would also cut off a legitimately large document.
* **This package verifies nothing.** It produces octets. Choosing which node
  set to digest, comparing digests in constant time where that matters, and
  validating the signature's structure against wrapping attacks are the
  verifier's job.

See [security.md](security.md) for the parser limits and the threat model.

## Determinism

The same input and options produce the same octets, every time, on every
platform. Namespace declarations are sorted by prefix, attributes by namespace
URI then local name, both by byte comparison of UTF-8 — which is code-point
order, as the specifications require, with no collation and no locale. No map
iteration order reaches the output. The tests canonicalize one input a
thousand times and require one result.

## Streaming

`Write` and `WriteNodeSet` stream to an `io.Writer` through a buffer; `Digest`
writes straight into the hash. Memory is bounded by the element depth and the
attribute count of one element, not by the document's size — the walk's
stacks are truncated rather than reallocated as it returns, so a steady-state
element allocates nothing. The input tree itself is, of course, in memory: the
parser builds it.

## Errors

| Error | When |
|---|---|
| `ErrNoAlgorithm` | `Options.Algorithm` is empty |
| `ErrUnsupportedAlgorithm` | the algorithm is not one of the six constants; wrapped with the value, so use `errors.Is` |
| `ErrUnsupportedNode` | `Bytes`/`Write`/`Digest` was given a node that is neither a document nor an element, or a node set whose `Root()` is nil |
| `ErrDepthExceeded` | nesting exceeds `MaxDepth` |
| `ErrRelativeNamespaceURI` | a namespace declaration that can reach the output binds a relative URI; wrapped with the declaration |
| `ErrXML11` | the tree was parsed from an XML 1.1 document |
| a write error from `w` | returned **unwrapped**, so `errors.Is` against your own sentinel works; the walk stops at the next element boundary |
| an `xpath` error | from `FromXPath`, when the expression does not compile or evaluate |

## xdm audit

Canonicalization needs six things from the data model, and the design
considered two ways of getting them if `xdm` did not already expose them: (A)
moving the parser's internals under `internal/` so `c14n` could reach them, or
(B) adding new exported API to `xdm`. Neither was needed. Each requirement,
against `xdm`'s public API as it stands:

| # | Requirement | Where `xdm` provides it | Public? |
|---|---|---|---|
| R1 | The namespace declarations made *on* each element, as written | `Node.Namespaces` — the declarations on that element only, an undeclaration (`xmlns=""`) carried as an empty value | yes |
| R2 | The bindings *in scope* at an element | `Node.InScopeNamespaces()` (a prefix-to-URI map, `xml` always present) and `Node.LookupPrefix(prefix)` for one prefix | yes |
| R3 | `xml:*` attributes, for inheritance and the 1.1 `xml:base` fix-up | ordinary `Node.Attrs` whose `Name.URI == xdm.NSXML` | yes |
| R4 | Document order | `Node.Compare` orders any two nodes. `Node.Order()` is a per-tree index assigned by `Tree.Finalize` in one pre-order walk, which every parser entry point calls; it is strictly increasing in document order within a finalized tree but **not dense** — `Finalize` reserves a slot for every in-scope binding of each element, for the namespace-axis nodes synthesized on demand, and adds a per-tree offset. `c14n` needs neither: it walks `Children` and `Attrs` in order and sorts what the specifications tell it to sort | yes |
| R5 | Node identity, for node-set membership | pointer equality for every node the parser builds; `Node.Is` for the general case (it differs only for synthesized namespace nodes, which never reach `c14n`) | yes |
| R6 | Character data in canonical shape | the parser resolves character and entity references, merges CDATA sections with adjacent text into one text node, normalises CRLF and a lone CR to LF, keeps a `&#13;` reference as a literal CR (which C14N then writes as `&#xD;`), and normalises attribute whitespace — including, now, the collapse for attributes declared non-CDATA; verified by the `c14n` tests | yes |

**All six were already public, so options A and B were unnecessary.** One field
was added for a different reason: `Tree.XMLVersion`, so that `c14n` can refuse
XML 1.1 input (see [Refused input](#refused-input)).

Canonicalization is only as correct as the parser under it, and building it
found four parser defects, each of which would have changed a digest. All are
fixed in `xdm`:

* An attribute declared non-CDATA in the internal subset (`NMTOKENS`, `ID`, an
  enumeration, `NOTATION`, …) kept leading, trailing and repeated spaces, where
  XML 1.0 §3.3.3 collapses them; a `NOTATION` list was also misread as the
  default. C14N 1.0 example 3.4 needed it.
* A character reference in an entity value was expanded one level short:
  `<!ENTITY a "&#38;#38;">` gave `&#38;`, not `&` (XML 1.0 Appendix D).
* An ATTLIST default `xmlns:p` for an element named `p:doc` did not reach it:
  the declaration was matched by local name only.
* Line ends were folded by the tokeniser, too late: CR-LF in an attribute value
  became two spaces, and a CR survived in comments and processing
  instructions. XML 1.0 §2.11 is now applied on input, before parsing
  (`xdm/lineend.go`).

### Where `xmlsec1` differs

Twelve inputs account for all 108 differences. On nine of them (88
differences) `xmlsec1` departs from a Recommendation; on the other three (20),
the partial namespace axes below, it follows the non-normative reading of
Exclusive C14N §3.1 where this package follows the normative §3. The test
asserts each difference exactly, per reference and PrefixList — the octets
`xmlsec1` produces, or the error it stops with — so an entry fails the day
`xmlsec1` agrees.

Naming a prefix bound nowhere on the PrefixList changes neither side's output:
each list with `nosuchprefix` gives what the list without it gives, and the
differences it meets are the ones the rest of the list already produces.

#### Reference defects

* **DTD default attributes are not applied** (`dtd-default-attr`,
  `dtd-default-ns-attr`). `xmlsec1`'s command line parses without adding
  attributes a DTD defaults; C14N 1.0 §1.1: "Default attributes are added to
  each element". `xmllint` adds them and agrees with this package.
* **Entity references are not replaced** (`dtd-internal-entity`). `xmlsec1`
  leaves the reference in the tree and libxml2's canonicalizer then refuses
  it ("Node XML_ENTITY_REF_NODE is invalid here"); C14N 1.0 §1.1: "Character
  and parsed entity references are replaced".
* **A defaulted `xml:space` is not inherited** (C14N 1.0 §3.7, C14N 1.1 §3.8,
  and the interop cases `xmlbase-c14n11spec-102` and `xmlbase-c14n11spec2-102`,
  under the four inclusive algorithms). Each declares `<!ATTLIST e2 xml:space
  (default|preserve) 'preserve'>` and omits `e2`, so the Recommendations print
  `xml:space="preserve"` on `e3`, and all five interop implementations signed
  that. The cause is the one above: with the attribute written out, `xmlsec1`
  agrees. Under C14N 1.1, libxml2 also renders the attribute declaration it
  finds instead, as `space=""`.
* **An `xmlns=""` undeclaration rendered as text** (C14N 1.0 §4.7, first
  input, under the inclusive algorithms and Exclusive C14N with `#default` in
  the PrefixList). The filter omits `e2` but keeps its namespace nodes, and
  libxml2 models `e2`'s `xmlns=""` as one, so it prints ` xmlns=""` between
  `e1`'s start tag and `e3`. XPath 1.0 §5.4 gives an undeclaration no
  namespace node, so there is nothing to render. The same text recurs where a
  filter drops an element with `xmlns=""` but keeps the rest of its axis
  (`undeclaring-element-dropped`).

#### A difference of reading

* **Partial namespace axes under Exclusive C14N** (the `NamespaceSet`
  inputs `default-node-dropped-on-one-element`, `default-node-dropped-rebound`
  and `prefix-node-dropped-everywhere`). libxml2's exclusive canonicalizer decides namespaces from its own
  stack of rendered declarations — the non-normative "constrained
  implementation" of Exclusive C14N §3.1, which assumes an element's whole
  namespace axis is in the set exactly when the element is. Where the filter
  splits an axis, the normative text decides otherwise:
  * a default namespace node dropped on one element: §3's `xmlns=""`
    conditions all hold for that element, and `xmlsec1` omits it;
  * the same, where the dropped node binds a different URI from the
    ancestor's: §3 renders it, since its element is in the set and utilises
    it; `xmlsec1` renders a prefixed node in that position but not the
    default one;
  * a prefix on the PrefixList whose nodes the filter removed: §3 hands it to
    Canonical XML's rule, which renders only nodes in the set; `xmlsec1`
    renders it from its stack.

  In each, `xmlsec1`'s own *inclusive* output for the same input agrees with
  this package wherever the PrefixList sends the prefix to Canonical XML's
  rule.

**Throughput against `xmlsec1`.** `TestC14NThroughputXMLSec1` signs the
benchmark documents above with an enveloped signature — enveloped-signature
transform, `Inclusive10`, SHA-256 — in the same container as `xmlsec1`
(Docker Desktop, Apple M3 Pro, 12 CPUs, Debian 13 arm64, Go 1.25.14, `xmlsec1`
1.2.41). Two comparisons, each like with like: *with parse*, `xmlsec1
